** Introduction
<<cap.intro>>

High-Performance Computing (HPC) platforms combine multi-core CPUs and
GPUs, often in nodes of different generations. Programming such
platforms directly, deciding where each computation runs and when each
data transfer happens, is complex and does not port well from one
platform to another. Task-based programming addresses this problem: the
application is expressed as a Directed Acyclic Graph (DAG) of tasks
with their data dependencies, and a runtime system, such as StarPU
\cite{augonnet2011starpu}, maps the tasks to the resources, transfers
the data, and balances the load at execution time. The programmer still
decides, however, which resources the application uses, and in
particular on how many nodes it runs.

This decision is harder for applications made of phases with different
computational profiles. ExaGeoStat \cite{abdulah2018exageostat}, a
geostatistics application, is an example. Each iteration of its
Maximum Likelihood Estimation (MLE) first generates a covariance
matrix, an embarrassingly parallel phase that runs on CPUs, and then
factorizes it with a Cholesky factorization, a phase with many
dependencies and communications that benefits from GPUs. On a
heterogeneous platform, adding nodes speeds up the generation but may
slow down the factorization, because the extra nodes add
communications and are slower than the GPU nodes. Using all nodes in
both phases, the default choice, is therefore not necessarily the
fastest.

\citeonline{nesi2022ipdps} exploited this difference. They removed the
synchronization between the two phases, so that the factorization
starts while the generation is still running, and gave each phase its
own data distribution, with the generation on all nodes and the
factorization on a subset of them. Since the best number of
factorization nodes depends on the platform and on the problem, they
proposed to learn it online, during the iterations of a single
execution, with a Gaussian process guided by a lower bound computed by
a linear program. This strategy found good configurations in few
iterations and reduced the execution time compared to using all nodes
in both phases.

Three questions remain open after that work. First, the selection has
only one dimension: the generation always uses all nodes, although the
number of generation nodes could also be chosen. Second, the objective
is only time. With the per-phase execution, some nodes stay idle during
a phase, and configurations with similar time may use different
numbers of nodes and thus consume different amounts of energy. Third,
the implementation is a patch on the legacy version of ExaGeoStat, on
top of versions of StarPU and Chameleon that are no longer maintained,
and the current version of the application, ExaGeoStatCPP, does not
include the per-phase execution.

This work addresses these three questions. Its main objective is to
learn online, during a single execution of a multi-phase task-based
application, how many nodes each phase should use, with energy
consumption as part of the objective. The expected contributions are:
(i) the per-phase execution of ExaGeoStat on the current software
stack, packaged for reproducibility; (ii) an online strategy that
selects jointly the number of generation and factorization nodes; and
(iii) the inclusion of energy in this selection, with measurements on
real hardware.

The remainder of this document is organized as follows. Section
[[sec.motivation]] quantifies, from the data published by
\citeonline{nesi2022ipdps}, how much the second dimension brings and
why energy matters for it. Chapter [[cap.objectives]] details the
objectives and the expected results. Chapter [[cap.related]] discusses
the related work. Chapter [[cap.methodology]] presents the
methodology, and Section [[sec.schedule]] the schedule.

The online selection of \citeonline{nesi2022ipdps} fixes the
generation on all nodes and learns only the number of factorization
nodes. Their Figure 8, however, explores both dimensions for one
scenario: it presents the iteration time of every pair (generation nodes,
factorization nodes) with at least as many generation nodes as
factorization nodes. The platform has 23 heterogeneous Grid'5000 nodes
of three types (15 Chetemi, 6 Chifflet, and 2 Chifflot). We
quantified this data, and Figure \ref{fig.motivation} and Table
\ref{tab.motivation} summarize the result.

The one-dimensional selection already captures most of the gain: using
9 factorization nodes and all nodes for the generation reduces the
iteration time by 17.4% compared to using all nodes in both phases,
while the best pair overall reduces it by 20.0%. The second dimension
therefore adds only 3.2% over the best one-dimensional configuration.
Moreover, the region around the best pair is flat. With 8
factorization nodes, any number of generation nodes between 9 and 16
gives an iteration time within 0.34 s (1%) of the best. Considering
only time, these configurations are equivalent, and an online
strategy would spend iterations exploring a dimension that brings
little.

Energy breaks this tie. If the nodes that no phase uses are released,
generating on 9 nodes instead of 16 uses 7 fewer nodes for practically
the same iteration time. Even if the nodes stay reserved, idle nodes
typically consume less power than active ones. The configurations that
time cannot distinguish thus differ in energy, which is why the joint
selection of the number of nodes of both phases is relevant when energy
is part of the objective.
The energy study in the thesis of Nesi,
which measured time and energy for a sweep of generation and
factorization nodes on Grid'5000 Lille but did not optimize for
energy, points in the same direction.

This analysis has limitations. It covers a single scenario, with one
measurement per pair, and the data comes from a simulated execution.
In addition, two of the three node types of this scenario are no
longer available in Grid'5000, so the scenario can only be reproduced
in simulation. Characterizing when the second dimension matters, in
time and in energy, on current platforms is part of the objectives of
this work.

** Objectives
<<cap.objectives>>

The main objective of this work is to learn online, during a single
execution of a multi-phase task-based application, how many nodes each
phase should use, with energy consumption as part of the objective.
We use the ExaGeoStat geostatistics application as the case study.
Each iteration of its Maximum Likelihood Estimation (MLE) has two
phases with different profiles: the generation of the covariance
matrix and its Cholesky factorization. The selection is made jointly
for both phases, the number of nodes for the generation and the number
of nodes for the factorization, while the application runs. This
extends the one-dimensional selection of \citeonline{nesi2022ipdps},
in which the generation always uses all nodes. To reach this goal, we
define three specific objectives:

- *O1. Bring the per-phase execution to the current software stack.*
  Implement the asynchronous execution of the two phases and a
  separate data distribution for each phase in ExaGeoStatCPP, the
  current version of ExaGeoStat, on top of StarPU 1.4 and Chameleon
  1.4, with the whole stack packaged in Nix for reproducibility.
  Success criterion: reproduce the gain of the one-dimensional
  selection reported by \citeonline{nesi2022ipdps} on a current
  platform (Grid'5000, Lille site).
- *O2. Select the number of nodes of both phases online.* Design and
  evaluate online strategies that choose the pair (generation nodes,
  factorization nodes) along the MLE iterations, with the Gaussian
  process approach of \citeonline{nesi2022ipdps} as the starting
  point. Success criterion: compare against using all nodes in both
  phases and against the one-dimensional selection, in cumulative
  execution time and regret.
- *O3. Include energy in the objective.* Extend the selection so that
  it minimizes energy consumption under a time constraint
  $T \leq (1+\varepsilon)\,T^{*}$, where $T^{*}$ is the best
  iteration time. Success criterion: energy measured with the
  wattmeters available in Grid'5000 Lille, and a characterization of
  the configurations in which the energy optimum differs from the time
  optimum.

*** Expected Results

At the end of this work, we expect to provide an up-to-date and
reproducible version of the per-phase execution of ExaGeoStat, an
online method that selects the resources of each phase, and a
quantification of the time and energy gains of this selection
compared to the one-dimensional selection and to using all nodes.

For O1, we expect a software stack based on current releases of
StarPU, Chameleon, and ExaGeoStatCPP that reproduces the asynchronous
execution with per-phase distributions. If a required feature is
missing in Chameleon or StarPU, we will document what is missing and
fall back to the legacy implementation as the base for O2 and O3, so
that the later objectives do not depend on the complete port.

For O2, we expect to identify the scenarios in which the second
dimension pays for its additional exploration and the scenarios in
which it does not. Our preliminary analysis (Section
[[sec.motivation]]) suggests that, considering only time, the gain
of the second dimension can be small. A map of when the
one-dimensional selection is already enough is also an acceptable
result.

For O3, we expect to show in which configurations the energy optimum
diverges from the time optimum and how much energy can be saved within
the time tolerance $\varepsilon$. If energy follows time in our
platforms, we will report under which energy accounting this happens
(nodes reserved for the whole execution or nodes released when a phase
does not use them) and why.

*** ExaGeoStat on Chameleon and StarPU
<<sec.exageostat>>

StarPU \cite{augonnet2011starpu} is a task-based runtime that uses the
Sequential Task Flow (STF) model. The application submits tasks
sequentially, declaring the data each task reads and writes, and the
runtime infers the dependencies, builds the Directed Acyclic Graph
(DAG) of tasks, and schedules each task to a CPU core or a GPU at
execution time. The runtime also transfers data between memories and
nodes, so that the same code runs on heterogeneous platforms. With
StarPU-MPI, each node submits the whole DAG, executes the tasks that
write data it owns, and exchanges data with the other nodes when a
dependency crosses nodes. The data distribution, that is, which node
owns each tile of a matrix, therefore defines where each task runs.
Chameleon \cite{agullo2010chameleon} is a dense linear algebra library
built on this model, which provides, among others, the tiled Cholesky
factorization.

ExaGeoStat \cite{abdulah2018exageostat} is a geostatistics application
that estimates the parameters of a spatial statistical model by
Maximum Likelihood Estimation (MLE). Each MLE iteration evaluates the
likelihood for a set of parameters proposed by an optimizer. The
evaluation has two dominant phases with different profiles. The
generation phase builds the covariance matrix: each tile is computed
independently from the locations and the parameters, which makes the
phase embarrassingly parallel and executed on CPUs. The factorization
phase computes the Cholesky factorization of this matrix with
Chameleon, which has many dependencies, communicates between nodes, and
benefits from GPUs. Because of these differences, the number of nodes
that minimizes the time of one phase is not necessarily the one that
minimizes the time of the other.

\citeonline{nesi2022ipdps} exploit this difference in two ways. First,
the phases run asynchronously: the factorization of a tile starts as
soon as the tile is generated, without waiting for the end of the
generation. Second, each phase has its own data distribution: the
generation uses all nodes, the factorization uses a subset of them,
and the tiles migrate between the two distributions. Then, the number
of factorization nodes is learned online, along the MLE iterations,
with a Gaussian process guided by a lower bound computed by a linear
program. This work keeps this execution model and adds the number of
generation nodes as a second dimension of the selection.

The implementation of \citeonline{nesi2022ipdps} is a patch on the
legacy version of ExaGeoStat, written in C, on top of versions of

no custom data distribution nor migration between phases. On the
other hand, recent versions of Chameleon provide a function to change
the distribution of a matrix asynchronously, which is equivalent to the
data migration implemented in the patch, but only with the StarPU

As a first step of O1, we packaged the stack in Nix: StarPU 1.4.12,
with FxT traces and StarPU-MPI, and Chameleon 1.4.0 with the StarPU
backend. ExaGeoStatCPP already compiles on top of these versions, with
small changes for Chameleon 1.4, and its data generation, MLE, and
prediction examples run on a small problem. The remaining steps of
O1 are: (i) remove the wait between the generation and the
factorization and use the asynchronous Cholesky factorization; (ii)
make the generation tasks aware of the data distribution, so that each
node generates only the tiles it owns; and (iii) change the
distribution between the phases with the asynchronous Chameleon
function. The execution traces of StarPU will be used to check that the
two phases overlap.

The experiments will run on two platforms. The PCAD cluster at
INF/UFRGS will be used for the development of O1 and for the first
multi-node runs. The Lille site of Grid'5000 will be used for the
validation of O1 and for O2 and O3. It combines CPU-only nodes
(chiclet) with GPU nodes (chifflot, with NVIDIA P100 and V100 GPUs),
which is the heterogeneity that makes the phases prefer different
numbers of nodes, and it provides wattmeters that measure the power of
each node. The energy study of Nesi's thesis used this same platform,
which allows comparing our measurements with the previous results.

Besides real executions, two tools reduce the cost of the evaluation.
StarPU-SimGrid \cite{stanisic2015simgrid} simulates the execution of a
StarPU application from performance models of the tasks and of the
platform, which allows studying platforms that are not available. The
resampling simulator of \citeonline{nesi2022ipdps} replays the
measured iteration times of each configuration, sampling one of the
measurements at each step, so that many online strategies can be
compared on the same data without new executions.

*** Evaluation
<<sec.evaluation>>

For O2, the strategies select a pair (generation nodes, factorization
nodes) at each MLE iteration. We will extend the Gaussian process of
\citeonline{nesi2022ipdps} to two dimensions, using a two-dimensional
lower bound to prune the search space, and compare it with GP-UCB
\cite{srinivas2010gpucb} and a reinforcement learning agent. The
baselines are: (i) all nodes in both phases, which is the default
behavior; (ii) the one-dimensional selection of
\citeonline{nesi2022ipdps}, with the generation on all nodes; (iii) a
rigid selection, with the same number of nodes in both phases; and
(iv) a random search. The metrics are the cumulative execution time
along the MLE iterations and the regret, defined as the difference
between the cumulative time of the strategy and that of the best fixed
configuration chosen in hindsight. The cumulative time captures the
cost of exploration, which is decisive when the application runs only
a few dozen iterations.

For O3, the objective becomes the minimization of the energy of an
iteration under the constraint $T \leq (1+\varepsilon)\,T^{*}$, where
$T^{*}$ is the best iteration time, which is itself unknown and must be
estimated online. The energy depends on how idle nodes are accounted
for. We will consider two cases: nodes reserved for the whole
execution, in which a node that a phase does not use still consumes
its idle power; and nodes released when no phase uses them, in which
they do not count. The time-only and energy-aware selections will be
compared in time, energy, and energy-delay product.

All experiments will follow a reproducible methodology. The software
stack is defined in Nix, the experiments are described and analyzed in
Org-mode documents, each configuration is measured several times in a
randomized order, and the results are reported with their confidence
intervals.
